## What to include in future entries

Use each changelog entry to describe what changed, why it matters, and how it affects your readers. You can keep the format lightweight or expand it with more detail as your project grows.

<Steps>
  <Step title="Record the release">
    Note the release date, version number, and a short summary of the change. Keep the summary specific and easy to scan.
  </Step>
  <Step title="Group the updates">
    Separate `New Features`, `Improvements`, and `Bug Fixes` so readers can find relevant changes quickly.
  </Step>
  <Step title="Link supporting content">
    Add references to deeper guides, setup instructions, or configuration notes when an update affects user workflows.
  </Step>
</Steps>

## Release note formats

<Tabs>
  <Tab title="Product release" icon="rocket">
    Use this format when you ship a user-facing improvement.

    ```md
    - Added export support for scheduled reports
    - Improved dashboard load time
    - Fixed an issue with session timeout handling
    ```
  </Tab>
  <Tab title="Documentation update" icon="book-open">
    Use this format when you update content without changing product behavior.

    ```md
    - Added a new onboarding guide
    - Clarified setup steps for first-time users
    - Updated examples to match the latest interface
    ```
  </Tab>
  <Tab title="Maintenance release" icon="settings">
    Use this format for internal cleanup, reliability, and polish.

    ```md
    - Improved validation for configuration values
    - Fixed broken links in the quickstart guide
    - Updated screenshots to match the current UI
    ```
  </Tab>
</Tabs>
